# Nayuta — BERT 活用 Android IME 設計書

> 状態: v0.2 — M0 完了（変換精度の実測結果は [m0-results.md](m0-results.md)）
> 最終更新: 2026-10-31

## 1. 目的

既存 IME の「文節単位のかな漢字変換」を、BERT による**文脈依存の候補採点**で置き換える。
さらに「カタカナ語 → 英単語」「ローマ字英単語の文脈補完」を同じ枠組みで扱う。

最終的には**自分用に毎日使える Android IME** を目指す。

## 2. 決定事項

| 項目 | 決定 |
|---|---|
| ゴール | 実用 IME（まず自分用に毎日使う） |
| BERT の役割 | 候補リランカー / 文節スパン分類器（生成器ではない） |
| 英語対応 | ①カタカナ語→英単語 ②ローマ字英単語の文脈補完（翻訳は対象外） |
| 推論場所 | 完全オンデバイス（通信なし） |
| 対象 OS | Android のみ |

## 3. 設計上の原則

1. **生成しない、採点する。**
   BERT は encoder なので、任意長の漢字列を自由生成させるのは不向き。
   「読みに対応する候補集合を文脈で並べ替える」問題として解く。これで
   未知語・人名・長さ不定の問題を回避できる。

2. **3 つの「単位」を分離する。**
   - モデルのトークン = **文字**（char-level BERT）
   - 探索の単位 = **単語**（ラティスのノード。読み→表記の曖昧性をここで解く）
   - UI の単位 = **文節**（単語列をルールベースでまとめた表示・選択の単位）

   単語スパン内の文字表現をプーリングして候補を分類し、確定後に文節へまとめる。
   これにより「文節ごとに区切る」という構想が、そのまま**部分変換 UI** に対応する。

   > 補足: 探索まで文節単位にすると、文節境界の曖昧性と表記の曖昧性が同時に絡み、
   > 候補数が組み合わせ爆発する。実在の IME も探索は単語ラティスで行い、
   > 文節は表示・選択の単位として後段で作る。本設計もそれに合わせる。

3. **変換（conversion）と予測（prediction）を混同しない。**
   次語予測は因果 LM の仕事で BERT の守備範囲外。
   本プロジェクトの BERT は「変換キー押下時の採点」に限定する。
   予測変換（入力途中のサジェスト）は別レイヤ（辞書 + 学習履歴）で担当する。

4. **端末内で完結。** 通信なし、入力内容を外部送信しない。

## 4. アーキテクチャ

```
[フリック/QWERTY]
        │ かな列（読み）
        ▼
┌─────────────────────────────────┐
│ ① 候補生成: 単語ラティス + Viterbi │  辞書（読み→表記+コスト）
│    → N-best 文節分割・表記 (N=32) │
└────────────────┬────────────────┘
                 │ N-best の全スパン
                 ▼
┌─────────────────────────────────┐
│ ② BERT 文節スパン分類器            │  1 回のバッチ forward
│   input : [文脈文字列] + [読み文字列] │
│   output: 各スパン × 各候補のスコア   │
└────────────────┬────────────────┘
                 │ score = 辞書コスト + α·log P_bert
                 ▼
┌─────────────────────────────────┐
│ ③ 再ランク → 候補ビュー表示        │
│   文節タップ → そのスパンの候補だけ  │
│   差し替え（部分変換）              │
└─────────────────────────────────┘
```

### 4.1 なぜ N-best リランク方式か

- 文節境界の探索と BERT 採点を同時にやると forward 回数が爆発する。
- 辞書 Viterbi で妥当な N-best を作り、**その中のスパンだけを 1 バッチで採点**すれば
  1 変換あたり forward 1 回で済む。
- 変換キー押下時のみ計算するので、打鍵ごとのレイテンシ問題を回避できる。

### 4.2 英語の扱い

- **カタカナ語 → 英単語**: 辞書の語彙エントリに英語表記を併記し、候補集合に混ぜる。
  例: `えんじにあ` → {エンジニア, engineer}。文脈で選ばれるので、
  開発者向け文脈では `engineer` が上位に来るようになる。追加コストほぼゼロ。
- **ローマ字英単語の文脈補完**: 英単語辞書（頻度付き）+ 文脈採点。
  日本語文脈中で `rea` → `react` を選ぶ、といった挙動。同じ採点器で扱う。

## 5. モデル仕様

### 5.1 入力

```
[CLS] <ct> 直前の文脈文字列（最大 64 文字）</ct>
      <rd> 変換対象の読み文字列（最大 48 文字）</rd> [SEP]
```

- **char-level**（サブワードではなく文字単位）。読みは仮名の連続で、
  漢字表記との対応は文字単位の方が自然に取れるため。
- 文脈は「確定済みテキストの末尾」＋「同一文節群の既変換部分」。

### 5.2 出力

読み中の各文節スパン `[s, e)` について、候補集合 `C_i` に対するスコア分布。

```
h_span = mean_pool(h_s … h_{e-1})
c_j    = mean_pool(char_emb(候補表記 j の各文字))   ← 候補埋め込み表を持たない
score_j = MLP([h_span ; c_j ; h_span ⊙ c_j])
P(j)   = softmax(score)
```

- 候補表記の埋め込みを**文字埋め込みから構成**することで、数十万語の表を持たずに済む
  （メモリ・モデルサイズ・未知語に強い）。

### 5.3 サイズと速度の目標

| 構成 | パラメータ | int8 概算 | 想定レイテンシ |
|---|---|---|---|
| 6 層 / 256 dim / 4 heads | 約 7M | 7–9 MB | 20–40 ms |
| 12 層 / 384 dim / 6 heads | 約 27M | 27–30 MB | 60–120 ms |

まず 12 層で品質上限を測り、その後 6 層へ蒸留して実機に載せる（2 段構え）。
レイテンシは実機実測で判断する。

### 5.4 学習

- 目的関数: 正解表記に対する cross-entropy（文節ごと）。
- 負例: 同じ読みを持つ別表記を辞書から列挙（自然な hard negative）。
- データ生成: コーパスの文 → 形態素解析 → 読み列と表記列のペアを自動生成。
  - 注意: 解析器の出力が正解になるため「解析器より賢くはならない」。
    伸びるのは**文脈で曖昧性を解く部分**（同音異義語の選択）。
- 評価: 文節正解率 / 文単位正解率。ベースラインは辞書 Viterbi 単体。

## 6. Android 実装

| 層 | 実装 |
|---|---|
| IME | `InputMethodService` + 自作キーボード View（`KeyboardView` は非推奨） |
| 変換 | Kotlin: ラティス構築 / Viterbi / N-best / 再ランク |
| 推論 | ONNX Runtime Android（int8 量子化モデル） |
| 辞書 | 読み→表記+コスト（SudachiDict / IPADIC 由来、端末内 SQLite or バイナリ） |
| 学習 | ユーザー選択履歴をカウントし辞書コストへ反映（モデルの再学習はしない） |

### 配布・サイズ

- モデルは APK に同梱せず、初回起動時に asset から展開 or Play Asset Delivery。
- 目標: APK 15 MB + モデル 10–30 MB + 辞書 10–20 MB。
