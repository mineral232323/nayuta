# M0 結果レポート — BERT はかな漢字変換に効くか

> 実施日: 2026-10-30 / 状態: M0 完了

## 1. 問い

「読み（かな）→ 表記（漢字）」の候補選択において、
文字レベル BERT の文脈採点は辞書 unigram ベースラインより精度を上げるか。
また、その改善は**どこから**来ているのか（前方文脈か、文内の読み文脈か、単なる頻度学習か）。

## 2. 実験設定

| 項目 | 内容 |
|---|---|
| コーパス | 日本語 Wikipedia 2023-11-01 の 60,001 記事 |
| 変換単位 | 単語（Sudachi の形態素。文節は UI 側で後段に作る） |
| 学習データ | 244 万文 → うち 70 万文を 1 epoch |
| 検証データ | 24,422 文 |
| 辞書 | 学習コーパスから自動構築（読み → 表記 + 頻度）。22.7 万エントリ |
| ベースライン | 辞書 unigram コストのみの Viterbi |
| 提案手法 | 単語ラティス + 文字 BERT のスパン採点（`cost = unigram − β·log P_bert`）で Viterbi |
| エンコーダ | `tohoku-nlp/bert-base-japanese-char-v3`（char-level, 7,027 字語彙, 110M） |
| 追加パラメータ | スパン/候補相互作用の MLP のみ（約 1.8M） |

入力は `[CLS] 直前の文脈（最大64字）[SEP] 読み（最大48字）[SEP]`。
各読みスパンの表現と候補表記の文字埋め込み平均からスコアを出す。

## 3. 結果

### 3.1 変換精度（検証 2,000 文）

| 指標 | unigram | BERT | 差 |
|---|---|---|---|
| 候補選択精度（正解分割を与えた場合） | 89.79% | **93.67%** | +3.9pt |
| 文正解率（分割探索込み, β=2） | 38.15% | **52.05%** | +13.9pt |

内訳: BERT だけ正解 313 文 / ベースラインだけ正解 35 文（差し引き +278 文）。
**エラーが約 22% 減った**（61.85% → 47.95%）。

β（BERT スコアの重み）は 1〜4 が最良で、8 まで上げると劣化する（ベースラインの prior を捨てすぎる）。

### 3.2 改善はどこから来たか（正解分割を与えた候補選択精度）

| 条件 | 全体 | 前方文脈あり | 前方文脈なし |
|---|---|---|---|
| A. unigram（頻度のみ） | 89.88% | 92.05% | 87.83% |
| B. BERT（単語の読みのみ） | 77.51% | 76.54% | 78.43% |
| C. BERT（文全体の読み） | 93.04% | 94.54% | 91.63% |
| D. BERT（文全体 + 前方文脈） | **93.53%** | **95.56%** | 91.63% |

読み方:

- **B → C（+15.5pt）が最大の伸び**。同音異義語の解決に効いているのは
  「文全体の読み」という文内文脈であり、これが BERT の主な貢献。
- **C → D（前方文脈あり群で +1.02pt）** が前方文脈の純粋な寄与。
  対象が限られる（検証スパンの 48%）ため全体では +0.5pt 程度だが、
  同一スパンでの paired 比較なので有意な差。
- B が unigram より低いのは、単語単体では BERT が持つ頻度知識が入らないため。
  「BERT 単体 < unigram」ではなく「**文脈を与えたときだけ BERT が prior を超える**」構図。

## 4. 考察

1. **設計仮説は支持された。** 投票型の生成ではなく「候補の文脈採点」として BERT を使う方針は、
   実測でエラー 22% 減。しかも 1 回の forward で全スパンを採点できるため、レイテンシ設計とも整合する。
2. **文脈の作り方に改善余地がある。** 初回のデータ生成では、段落内の文が 1 つ捨てられるたびに
   文脈バッファをリセットしていたため、学習例の **13.7%** にしか前方文脈が入っていなかった。
   修正後は 34.8%。それでも低いのは、Wikipedia の段落が 1〜2 文で終わることが多いため。
3. **前方文脈の効果は実装コストに対して見合う。** C→D の +1pt は、Android では
   `getCurrentInputConnection().getTextBeforeCursor()` でそのまま取れる情報だけで得られる。
4. **文正解率 52% は「実用水準」ではない。** ベースラインが意図的に弱い（unigram のみ）ため。
   実用 IME の比較対象は Mozc / Google 日本語入力であり、そこに追いつくには
   辞書・連接コスト・学習データ量の強化が別途必要。

## 5. ボトルネック（実測で分かったこと）

| 項目 | 現状 | 目標 | 課題 |
|---|---|---|---|
| モデルサイズ | fp32 361 MB | int8 10〜30 MB | 蒸留 + 量子化（M1） |
| 推論 | GPU で 1 文 ~15 ms | 端末で 1 変換 100 ms 未満 | 蒸留後に実機実測 |
| 辞書 | コーパス由来 22.7 万語 | 実用品質の語彙 + 連接コスト | Mozc/UniDic 系の活用 |
| 未知語 | 1 文字 kana フォールバックのみ | 人名・専門用語 | 未知語モデル / 学習データ拡充 |

## 6. 次の一手（優先順）

1. **M1: 蒸留と端末化** — 6 層 / 384 次元への蒸留 → int8 ONNX → 実機レイテンシ実測。
   ここが通らないと「毎日使う」に到達しない。
2. **辞書の強化** — コーパス由来辞書から、連接コスト付きの辞書（Mozc/UniDic 系）へ。
   これでベースライン自体が実用水準に近づき、比較が意味を持つようになる。
3. **学習データ拡充** — 70 万文 → 全 244 万文、さらに Wikipedia の残り shard。
4. **文節まとめと部分変換 UI** — 単語列 → 文節のルールベースまとめ（`android/` 側）。
5. **英語候補** — カタカナ語に英語表記を併記し候補集合へ追加（設計書 §4.2）。

## 7. 再現手順

```bash
export UV_CACHE_DIR=$PWD/.cache/uv HF_HOME=$PWD/.cache/huggingface

# データ生成（約 8 分）
.venv/bin/python -m train.prep_data --limit-articles 60000 --out-dir data

# 学習（約 25 分, RTX 5070 Ti）
.venv/bin/python -m train.train --data-dir data --limit 700000 --out models/scorer_v2.pt

# 評価
.venv/bin/python -m train.evaluate --checkpoint models/scorer_v2.pt --betas 2.0,4.0
.venv/bin/python -m train.analyze  --checkpoint models/scorer_v2.pt
```
